# 开发用到的 AI（中级）

####一、MCP（模型上下文协议）

* MCP（模型上下文协议）是一种用于将 AI 应用程序连接到外部系统的开源标准。使用 MCP，Claude 或 ChatGPT 等 AI 应用程序可以连接到数据源（例如本地文件、数据库）、工具（例如搜索引擎、计算器）和工作流程（例如专门的提示），从而使它们能够访问关键信息并执行任务。
* **一点思考**：有人可能会觉得“MCP 更应该叫函数调用，Function Calling 叫做 MCP 更好”——但实际上两者处于不同层面：**MCP 是协议**，规定了统一的工具发现与调用方式；**Function Calling 是模型的原生能力**，使模型能够理解并调用工具。两者是互补而非等同的关系。

####二、Function Calling

* Function Calling 是大语言模型（如 GPT）的一种**原生能力**。它允许模型在生成回答时，输出一个结构化的指令（函数名 + 参数），而不是纯文本。开发者根据这个指令去执行真实的函数，并将结果返回给模型，从而实现模型与外部工具的交互。

* 现代 LLM（如 GPT-4）在训练过程中，不仅学习了大量的自然语言文本，还通过**指令微调**和**工具使用示例**学会了如何响应函数调用指令。训练数据中包含类似这样的对话：

> **用户**：北京的天气怎么样？
> **助手**：我可以帮你查询天气。让我调用 `get_weather` 函数。
> **函数调用**：`get_weather(city="北京")`
> **函数结果**：晴，25℃
> **助手**：北京今天天气晴朗，气温 25 摄氏度。

* Function Calling 的典型步骤
  1. **用户调用大模型 API**，并附带可用的工具（tools）列表。
  2. **大模型 API 将工具列表连同对话上下文一起传给大模型**。
  3. **大模型分析后，选择需要调用的工具并生成调用参数**，将结果（函数名 + 参数）返回给 API。
  4. **API 执行真实的函数调用**（或由开发者执行），获取结果。
  5. **API 将函数执行结果与之前的对话历史一起再次发给大模型**。
  6. **大模型根据结果生成最终的自然语言回答**，API 将其返回给用户。

* **Function Calling 就是模型能够使用工具的一种能力。**：具体来说：模型能够**解析工具列表**，并能选出需要的工具名称和构造参数，能**解析工具的执行结果**，这种能力称为 Function Calling。





####三、MCP 与 Function Calling 的关系

- **Function Calling** 是模型内部的**能力**，让模型懂得“如何请求调用工具”。
- **MCP** 是外部的**协议**，定义了模型（或智能体）如何**发现**第三方工具、如何**调用**它们、如何**交换数据**的统一标准。

* 两者并不冲突，而是**天然互补**：

  * Function Calling 让模型“想要”用工具，MCP 让模型“知道”有哪些工具可用以及如何调用。可以类比为：

    - Function Calling = 人能理解“我需要打电话”这一意图；

    - MCP = 通用的电话通信协议（如 SIP），让不同品牌的电话能够互相拨打。

* MCP是外部和大模型API或者大模型的外围服务器的交互 ，Fuction Calling是大模型通过训练得到的能力。这种能力是通过训练（指令微调等）获得的。

  * 详细解释
    * Function Calling 是模型在预训练和指令微调阶段学习到的**原生能力**，使其能够根据对话上下文输出结构化的函数调用指令（函数名+参数）。
    * MCP 是**协议标准**，它定义了**客户端（如智能体应用、IDE、Claude Desktop 等）**如何与**外部工具服务器**进行交互（包括发现工具列表、调用工具、获取结果等）。
    * 这个客户端通常**位于大模型 API 之外**，可以是大模型 API 的调用方（例如你的应用），也可以是大模型厂商提供的应用（如 Claude Desktop），但**不是大模型 API 本身**。大模型 API 通常只负责生成文本或函数调用请求，而 MCP 负责在应用层与外部服务通信。
    * 所以更精确的说法是：**MCP 是连接 AI 应用（它们调用大模型 API）与外部工具/数据源的标准化协议**。





####二、Agent Skill

* **定义**：Skill 是基于文件系统的可重用资源，为大模型提供特定领域的专业知识：工作流程、规则、数据上下文，可将通用代理转变为专家。与提示（针对一次性任务的对话级指令）不同，技能按需加载，无需在多个对话中重复提供相同的指导。

* **主要优势**：

  - **专精**：针对特定领域任务定制能力。

  - **减少重复**：一次创建，自动使用。

  - **整合能力**：结合各种技能构建复杂的工作流程。


* 基于文件系统的架构实现了**渐进式披露**：Claude 根据需要分阶段加载信息，而不是预先获取上下文。
  * “渐进式披露”——通过将技能内容按重要性和使用频率分级，只在必要的时候将必要的信息加载到大模型的上下文窗口中，从而在保持模型通用性的同时，赋予它深度专业能力，且不会无谓消耗宝贵的上下文资源。

* Skill 可以包含三种类型的内容，每种内容的加载时间各不相同：

  * 级别 1：元数据（始终加载）

    * 内容类型：说明该 skill 的 YAML 前置元数据提供发现信息。

      ```txt
      ---
      name: pdf-processing
      description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
      ---
      ```

    - 元数据非常轻量，每个技能仅消耗约 100 个 token，即使安装上百个技能，总开销也有限。

    - **它的作用就像一个“目录”**，让模型**知道有哪些技能存在**，以及**每个技能是干什么的**（通过 description）。

    - 模型在理解用户问题时，会扫描这个“目录”。如果用户请求匹配了某个技能的描述，模型就知道“哦，这个问题可能需要用到‘PDF 处理’技能”。

    - 会在启动时加载这些元数据并将其包含在系统提示符中。这种轻量级方法意味着您可以安装许多技能而不会受到上下文影响；大模型只知道每个技能的存在以及何时使用它。

  * 级别 2：指令（触发时加载）

    * 内容类型：SKILL.md 的主体内容包含程序性知识：工作流程、最佳实践和指导原则。

      ````txt
      # PDF Processing
      
      ## Quick start
      
      Use pdfplumber to extract text from PDFs:
      
      ```python
      import pdfplumber
      
      with pdfplumber.open("document.pdf") as pdf:
          text = pdf.pages[0].extract_text()
      ```
      
      For advanced form filling, see [FORMS.md](FORMS.md).
      ````

    - 当请求的内容与技能描述相符时，大模型会通过 bash 从文件系统中读取 SKILL.md 文件。只有这样，该文件的内容才会显示在上下文窗口中。

    - **“按需加载”**：只有当你真正需要用到这个技能时，它的详细说明书才会被加载进来。平时它静静地待在文件系统里，不占用任何上下文 token。

    - **保证深度**：这份说明书可以写得非常详细（上限可达数千 token），为模型提供执行该任务所需的全部专业知识，让模型从“知道有这个工具”变成“知道怎么用这个工具”。


  * 级别 3：资源和代码（按需加载）:内容类型：说明、代码和资源。skill 可以捆绑其他材料

    ```txt
    pdf-skill/
    ├── SKILL.md (main instructions)
    ├── FORMS.md (form-filling guide)
    ├── REFERENCE.md (detailed API reference)
    └── scripts/
        └── fill_form.py (utility script)
    ```

    - **说明**：包含专门指导和工作流程的附加 Markdown 文件（FORMS.md、REFERENCE.md）。

    - **“引用而非包含”**：这些资源文件的内容**并不会被加载到模型的上下文窗口中**。模型只知道“有一个脚本叫 `fill_form.py`，它可以填表”，当需要时，它就去运行这个脚本，然后获取脚本的输出。

    - **无限扩展**：通过这种方式，技能可以附带任意大小的代码库、数据集或文档，而完全不受模型上下文窗口的限制。脚本执行的结果通常很短（如成功/失败状态、提取出的几行数据），只把必要的结果信息带回上下文，实现了高效的信息交互。


* **总结**：这种分级加载原理，实际上是将 Memory（长期记忆）、Function Calling（工具调用）和文件系统（外部存储）结合起来，形成的一套完整的技能管理方案：

  - **元数据**：相当于一种轻量级的、常驻的 Memory，告诉模型“你会什么”。

  - **指令**：相当于动态加载的 Prompt，为当前任务提供深度指导。

  - **资源/代码**：相当于通过 Function Calling 或 MCP 调用的外部工具，提供确定性的执行能力，且结果只返回必要信息，不污染上下文。


* 系统提示词从指导操作变成了模型的“基本盘”——定义身份、通用规则、基础约束。它像操作系统的内核，始终运行。

* Skill 解放了 prompt 和工作流的部分逻辑，是模型的“应用软件”——按需安装、按需运行的专业知识包。它像安装在不同目录下的应用程序，只在需要时启动。
* 三级汇总

| 等级             | 加载时           | token 成本                | 内容                                           |
| :--------------- | :--------------- | :------------------------ | :--------------------------------------------- |
| 一级：元数据     | 始终（在启动时） | 每项技能约需 100 个 token | name 以及 description 来自 YAML 前置元数据     |
| 第二级：说明     | 技能触发时       | 低于 5000 个 token        | SKILL.md 正文包含说明和指导                    |
| 3 级及以上：资源 | 根据需要         | 实际上无限                | 通过 bash 执行的捆绑文件未将内容加载到上下文中 |





####三、大模型参数

* **Temperature** 和 **Top-p** 是控制大语言模型生成文本时随机性和多样性的两个核心参数。它们决定了模型在回答你的问题时，是每次都给出最确定的答案，还是会有一些“创意”的变化。

* Temperature**工作原理**：模型在预测下一个词时，会给词表中的每个词一个概率分数（比如“吃”：0.4，“喝”：0.3，“玩”：0.2……）。Temperature 参数会重新调整这些概率。

  - 当 **Temperature < 1**（如 0.5）：除以一个小于 1 的数，相当于放大 logits 之间的差异。Softmax 后，高概率的词概率变得更高，低概率的词几乎消失 → **确定性增强**。

  - 当 **Temperature > 1**（如 1.5）：除以一个大于 1 的数，相当于**缩小 logits 之间的差异**。Softmax 后，概率分布变得更平坦，低概率词也有机会被选中 → **多样性增强**。

  - 当 **Temperature = 1**：原始分布，不做调整。

  * 从 Softmax 的角度看：Temperature 是通过缩放 Softmax 的输入（logits），来控制概率分布的“锐度”。

* Top-p：Top-p 是在 Softmax 输出的概率分布上，动态地截断尾部，只保留核心概率质量。p 值越大，保留的候选词越多；p 值越小，保留的候选词越少。

  1. Softmax 先算出所有词的概率（这一步已经完成了）。
  1. 将所有词按概率从高到低排序。
  1. 从最高的开始累加概率，直到累加和达到 p 值（如 0.9）。
  1. 将这些词保留作为候选集，其余词的概率被设为 0。
  1. 在候选集内重新归一化概率（让它们加起来等于 1）。

  * **举例**：假设模型预测下一个词，有三个候选词：

  | 词   | 原始 logits | Softmax 概率 (T=1) | Temperature 0.8 后 logits | 新概率 (T=0.8) | Top-p=0.9 筛选后  |
  | :--- | :---------- | :----------------- | :------------------------ | :------------- | :---------------- |
  | "吃" | 5.0         | 0.70               | 5.0/0.8=6.25              | 0.85           | 保留 (累计 0.85)  |
  | "喝" | 4.0         | 0.25               | 4.0/0.8=5.0               | 0.14           | 保留 (累计 0.99)  |
  | "玩" | 2.0         | 0.05               | 2.0/0.8=2.5               | 0.01           | 丢弃 (累计超 0.9) |



* 其他重要参数

  1.**Top-k 采样**

- **作用**：限制候选词的范围，只保留概率最高的 k 个词，然后在这 k 个词中重新分配概率进行采样。
- **原理**：将概率最高的 k 个词保留，其余词概率置 0，再归一化。k 越小，候选越少，输出越保守；k 越大，候选越多，多样性增加。
- **与 Top-p 的区别**：Top-k 是**固定数量**截断，Top-p 是**动态数量**截断（根据累积概率）。实践中两者可结合使用，比如先 Top-k 再 Top-p。

2. **频率惩罚（Frequency Penalty）**

   - **作用**：减少模型重复使用相同的词或短语。

   - **原理**：根据词在已生成文本中出现的频率，对其 logits 施加惩罚（减去一个与出现次数成正比的系数）。出现次数越多，被选中的概率越低。

   - **典型值**：0 ~ 2 之间，正值惩罚重复，负值鼓励重复。

3. **存在惩罚（Presence Penalty）**

   - **作用**：鼓励模型谈论新话题，防止话题局限。

   - **原理**：与频率惩罚类似，但惩罚仅基于词是否出现过（二值），而不是出现次数。只要词出现过一次，就施加固定惩罚，使其后续更难被选中。

   - **典型值**：0 ~ 2 之间，正值鼓励引入新词。

4. **最大生成长度（Max Tokens）**

   - **作用**：限制模型生成的最大 token 数量，防止无限制生成或消耗过多资源。

   - **注意**：包含输入和输出总长度，通常需要根据模型上下文窗口设置。

5. **停止序列（Stop Sequences）**

   - **作用**：指定一组字符串，当模型生成到这些字符串时立即停止生成。

   - **用途**：常用于控制输出格式，例如生成 JSON 时遇到 `}` 停止，或多轮对话中遇到用户标识停止。

6. **最佳候选数（Best Of）**

   - **作用**：让模型生成 n 个候选结果，并返回概率最高的那个（或按分数排序后选择）。

   - **注意**：会显著增加计算成本，常用于需要高质量输出的场景。

7. **对数偏置（Logit Bias）**

   - **作用**：直接对某些 token 的 logits 加上一个偏置值，从而强制提高或降低某些词出现的概率。

   - **用途**：敏感词过滤、关键词强化、固定格式输出等。



###四、大模型常见名词

- **提示词（Prompt）**：就是你给 AI 的指令，用来告诉 AI 你想让它做什么、怎么做。当前这一句指令就是 prompt。
- **系统提示词（System Prompt）**：是你在对话开始时给模型设定的固定身份和规则。它像是一个“开机自启动的程序”，只要对话存在，它就始终占据上下文窗口的一部分。
- **上下文（Context）**：在当前轮次的对话中，AI 为了理解你的 Prompt 并生成回复，所能看到的所有背景信息。这通常包含当前对话窗口里之前的所有对话内容，也可能包含上传的文件内容。
- **记忆（Memory）**：AI 在不同的对话 sessions（会话）之间，能够长期存储和调用的关于你的信息。它通常需要用户明确保存，或者是模型根据设定自动提炼的关键信息。本质上是大模型在后台对 context 的压缩，可以做个性化定制。
- **智能体（Agent）**：让大模型能够调用接口或者执行某种程序逻辑。
- **RAG**：本地知识输入到向量数据库，做向量匹配。
- **Function Calling**：大模型和接口之间约定好返回的 JSON 类型，JSON Schema。这个一般是 AI 项目用这个，应用于大模型和智能体之间。
- **MCP**：智能体和代码没有在一个项目里，没有解耦，对于其他的项目，需要大模型能够发现第三方工具有哪些，约定一个协议调用，应用于智能体和工具服务。
